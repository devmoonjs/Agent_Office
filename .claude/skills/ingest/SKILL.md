# /ingest [파일경로]

`00-Inbox/`에 사용자가 넣어둔 문서를 위키 지식으로 환류한다. 인자가 없으면 `00-Inbox/` 전체를 처리하고, 경로를 지정하면 해당 파일만 처리한다.

## 지원 형식

- `.md`, `.txt`: 직접 읽는다
- `.pdf`: Read 도구로 직접 읽는다
- `.docx`, `.rtf`: `textutil -convert txt <파일> -output <임시경로>`로 변환 후 읽는다 (macOS 내장)
- 이미지(화이트보드 사진 등): Read 도구로 시각적으로 읽는다
- **녹음 (`00-Inbox/recordings/`)**: 대시보드 녹음 버튼 또는 직접 투입된 오디오(.webm/.m4a 등). 처리 규약은 아래 "녹음 처리" 절 참조
- **화자 분리된 전사 텍스트**: 외부 STT 도구(Clova Note, Zoom, Teams 등)의 결과물을 `.md`/`.txt`로 투입한 경우. 아래 "화자 분리된 전사 처리" 절 참조 — 회의록으로 분류해 처리하되 화자 확정 절차가 추가된다
- 그 외 형식: 처리하지 않고 사용자에게 보고한다

## 녹음 처리 (00-Inbox/recordings/)

녹음 1건은 세 파일로 구성된다: `<id>.<확장자>`(오디오), `<id>.meta.json`(대시보드 인터뷰 답변 — topic/attendees/project/context), `<id>.transcript.md`(전사 스크립트).

1. **전사 확인**: `<id>.transcript.md`가 없으면 먼저 `bash 90-Meta/scripts/record_worker.sh` 실행 (mlx-whisper 전사; 수 분 소요 — 백그라운드 실행 권장)
2. **meta 권위 원칙**: `meta.json`의 `topic`/`attendees`/`project`는 사용자가 녹음 직후 직접 답한 값이므로 **frontmatter와 동급의 권위 출처**다. 회의록 frontmatter의 attendees는 meta 값을 그대로 쓰고, 전사에서 추론한 참석자는 보충으로만 쓴다
3. **화자 귀속**: 전사에 화자 라벨(SPEAKER_N 등)이 있으면 아래 **"화자 분리된 전사 처리"** 절을 따른다 — 실명을 추측하지 말고 라벨을 그대로 endpoint로 두고 사용자에게 지목받는다. 라벨이 없으면 호명 단서("○○ 질문 있어?")로만 추정하고, 그렇게 만든 화자 귀속 관계는 **`implied` + `question`** 으로 검토에 올린다. 어느 경우든 근거 없는 화자 귀속은 금지하고, 모르는 화자는 미상으로 남긴다
4. **회의록 생성**: meta + 전사로 회의록을 작성해 통상 meeting 절차(위키 환류, 관계 추출, 검토 JSON 저장)를 따른다
5. **아카이브**: 회의록 → `60-Sources/meetings/`, 오디오 → `60-Sources/meetings/recordings/`, 전사 → `60-Sources/meetings/transcripts/` (삭제 금지, 이동만). 회의록 frontmatter에 오디오·전사 상대경로를 `recording:`/`transcript:` 필드로 링크하고, meta.json의 `status`를 `ingested`로 갱신한다

## 화자 분리된 전사 처리

전사 스크립트에 화자 라벨이 있으면(자체 녹음의 whisperx 경로든, 외부 STT 도구의 결과물이든) **화자를 이름 유사도로 추정하지 않는다. 발화 내용을 근거로 사용자에게 지목받는다.**

1. **인식**: 문서에 화자 라벨 패턴이 3회 이상 반복되면 화자 분리 전사로 처리한다. 다음 표기를 모두 받아들인다 — `SPEAKER_00:`, `화자1:`, `화자 1)`, `[김철수]`, `Speaker A:`, `발화자2 -`. 라벨이 없으면 기존 타임스탬프 전사 규약(호명 단서 추정)을 따른다
2. **화자별 발화 수집**: 라벨별로 발화를 모아 검토 JSON의 `speakers` 배열을 만든다. 형식은 `90-Meta/review-ui/server.py` 상단 docstring을 따른다
3. **질문 대상 선정**: 발화 비중 상위 화자만 묻는다. 기준은 **발화 5회 이상 또는 전체 발화의 5% 이상**이고, 그래도 8명을 넘으면 비중 순으로 8명까지만 묻는다. 나머지는 미상으로 두고 관계를 만들지 않는다 — 두세 마디 한 사람을 그래프에 넣을 값어치가 없다. **잘라낸 화자 수는 보고에 명시한다**
4. **`address_hint` — 가장 강한 단서다. 있으면 반드시 채운다**: 해당 화자의 발화 **직전**에 호명이 있었는지 본다("김도연 팀장님, 어떻게 보세요?"). 있으면 그 문장을 인용해 넣는다. 자기소개("○○팀 김도연입니다")가 있으면 그것을 우선한다. 이 한 줄이 있으면 사용자가 고민 없이 지목한다
5. **`quotes` — 긴 발언이 아니라 식별력 높은 발언을 고른다**: 그 사람이 누구인지 드러내는 것을 2~3개 고른다. 소속·역할·담당 업무 언급, 결정을 내리는 대목, 다른 참석자를 지시·요청하는 대목 순으로 우선한다. 일반론이나 맞장구("네, 맞습니다")는 고르지 않는다. 각 인용은 한 문장으로 다듬되 발화 내용을 바꾸지 않는다
6. **`candidates`**: 녹음 `meta.json`의 `attendees` 또는 회의록 frontmatter의 `attendees`를 그대로 넣는다. 이미 그래프에 있는 인물인지는 UI가 판단하므로 여기서 거르지 않는다
7. **관계의 endpoint로 화자 id를 그대로 쓴다**: 확정 전이므로 실명을 추측해 넣지 않는다. `{"label": "Person", "key": "SPEAKER_01"}` 형태로 올리면 사용자가 확정한 이름이 UI에서 일괄 치환된다. **`speakers`에 올린 화자는 최소 `ATTENDED` 관계 하나를 갖게 한다** — 관계에 한 번도 등장하지 않는 화자는 확정 카드가 만들어지지 않아 물어볼 수 없다
8. **화자 과분할을 전제한다**: 화자 분리는 같은 사람을 여러 라벨로 쪼개는 일이 흔하다(목소리 톤 변화, 마이크 거리). 같은 사람으로 보이더라도 **임의로 합치지 않고 라벨별로 각각 올린다** — UI에 "앞에서 확인한 사람과 같아요" 선택지가 있어 사용자가 합친다
9. **화자 id는 별칭이 아니다**: `SPEAKER_01`은 이 녹음에서만 쓰는 임시 라벨이므로 Person의 `aliases`에 남기지 않는다 (UI가 이미 제외한다)

## 절차

0. **Inbox 실시간 확인 (생략 금지)**: 매 실행마다 반드시 `ls -la "00-Inbox/"`를 **새로 실행**해 현재 파일 목록을 확인한다. 같은 대화에서 이전에 본 Inbox 상태는 이미 낡은 정보다 — 사용자가 그 사이에 파일을 추가했을 수 있다. **도구 호출 없이 "비어있음"이라고 답하는 것을 금지한다** (2026-06-10 실제 오답 사례: 직전 처리 기억에 의존해 새 파일을 못 봄)

1. **분류**: 문서 내용을 읽고 유형을 판정한다 — `meeting`(회의록), `doc`(기술문서/스펙/아티클), `note`(단편 메모)
   - 파일 상단에 회의 설명 frontmatter(`type: meeting`, `meeting:`, `attendees:` — 템플릿: `90-Meta/templates/meeting-header.md`)가 있으면 무조건 `meeting`으로 분류한다
   - **선언 우선 원칙**: 이 frontmatter는 권위 출처다. Meeting 노드의 `topic`/`date`, `ATTENDED` 엣지, `WORKS_ON`(project 필드), 인물의 팀/역할 속성은 frontmatter 값을 그대로 사용하고, 본문 추론은 frontmatter에 없는 정보(결정, 액션 아이템, 논의 개념)를 보충하는 데만 쓴다. 본문에서 추론한 참석자가 frontmatter와 충돌하면 frontmatter를 따르고 충돌 사실을 보고한다
   - attendees의 `이름 (팀/역할)` 표기를 파싱해 Person의 `team`/`role` 속성으로 적재한다. 헤더가 없는 회의록은 본문 추론으로 처리하되, 보고에 "헤더 없음 — 추론 기반"을 명시하고 다음부터 템플릿 사용을 권한다
2. **지식 추출**: 유형별로 추출 대상이 다르다
   - **회의록**: 결정사항(decision), 액션 아이템, 논의된 기술 개념. 결정사항은 "무엇을, 왜, 대안은 무엇이었나" 구조로 추출한다
   - **'할 일' 섹션 필수 (생략 금지)**: 아카이브되는 모든 회의록 md에는 `## 할 일` 섹션을 반드시 둔다 — 이 회의로 어떤 할 일이 새로 생겼는지 항상 알 수 있어야 한다. 형식은 표 `| # | 할 일 | 담당 | 기한 | 프로젝트 |`. 할 일이 하나도 없으면 `## 할 일` 아래 "없음 — 결정·공유만 있었던 회의"라고 명시한다. 이 표의 각 행이 그래프 `ActionItem` 1개가 되며 검토 JSON에 `PRODUCED`(Meeting→ActionItem)·`ASSIGNED_TO`로 올린다
     - **워딩 규칙**: `desc`는 "무엇을 어떻게 한다"가 읽히는 **동사로 끝나는 한 문장**으로 쓴다. 명사구 축약("서비스 UI 개선", "자료 정리·체크")은 금지 — 회의 맥락을 모르는 사람이 읽어도 무슨 일인지 알 수 있게 대상·범위·산출물을 담는다 (예: "샘플 AI 서비스 UI 개선 항목(요구사항 결과 화면 중심)을 정리하고 적용한다")
     - **결정사항은 할 일이 아니다**: "~기능 논의 중단", "~로 확정" 같은 결정은 `Decision`으로 보내고 ActionItem으로 올리지 않는다
     - **props 필수**: `desc`, `project`(회의록 frontmatter `project:`의 표시명 — 예: "샘플 AI", "Project J"), `status: "open"`, `due`(모르면 빈 문자열). `project`가 없으면 홈 화면 '오늘 할 일'에서 어느 프로젝트 일인지 알 수 없다
     - **id 규칙**: `<meeting_id>#a<n>` 만 허용. 사람 이름 등이 id로 들어간 사례(2026-08-26)가 있어 적재 후 `WHERE NOT a.id CONTAINS '#'`로 0건을 확인한다
     - 완료 처리는 `python3 90-Meta/scripts/action_items.py done <id>` (삭제 대신 `status: done`, `done_at` 기록). 목록은 `action_items.py list --project <이름> --open`
   - **기술문서**: 핵심 개념/패턴/도구. 기존 위키 노트와 겹치면 해당 노트를 보강하고 `source`에 문서 출처를 추가한다
   - **단편 메모**: 위키화할 가치가 있는 항목만 선별한다
3. **위키 환류**: 추출된 각 개념에 대해 `/wiki-add`와 동일한 규칙 적용 — 중복 확인 후 신규 작성 또는 기존 보강, `90-Meta/templates/wiki-note.md` 구조, frontmatter `source`에 원본 문서 경로, MOC 등록, 백링크 2개 이상
4. **인물 관계 추출 — 사용자 컨펌 전 적재 금지**: 문서에서 인물·관계를 추출하되, **사용자가 승인하기 전에는 Neo4j에 절대 적재하지 않는다**
   - **추출 기준 (근거 강도 등급)**: 추출하는 모든 관계에 `confidence` 등급을 매긴다 — `direct`(문서에 관계를 직접 진술하는 문장이 존재) 또는 `implied`(직접 진술은 없으나 문서 정황상 강하게 시사됨). 두 등급 모두 `evidence`를 반드시 첨부한다: `direct`는 진술 문장 한 줄 인용, `implied`는 근거 정황 + 추론 한 줄. 근거를 전혀 댈 수 없으면(인용도 정황도 불가) 그 관계는 버린다 — 무근거 추측 금지. `implied` 관계는 검토표에 **기본 제외(체크 해제) 상태**로 올려 사용자가 명시적으로 포함을 선택하게 한다
   - **인물/조직 구분**: Person은 개인 이름만. 부서·팀·기관·협력사 명칭은 버리지 말고 **`Organization` 노드로 추출**한다 (`kind: internal`=사내 부서 — 조직도 시드와 이름 대조, `kind: external`=외부 기관/협력사). Organization이 endpoint로 허용되는 관계는 `ATTENDED`(기관 참석), `ASSIGNED_TO`(팀 담당), `WORKS_ON`(협력사 프로젝트 참여). 명칭이 인물인지 조직인지 애매하면 Person으로 올리되 검토 카드에서 사용자가 조직으로 전환할 수 있다 — 판단이 서지 않으면 질문을 남긴다
   - 추출 대상: 참석자(`ATTENDED`), 결정 책임자(`DECIDED`), 액션 아이템 담당(`ASSIGNED_TO`), 보고 관계(`REPORTS_TO`), 협업 관계(`WORKS_WITH`), 프로젝트 참여(`WORKS_ON`), 논의 개념(`DISCUSSED` — 위키 노트와 동일한 `name` 사용)
   - **검토 데이터 저장 (생략 금지 — 컨펌 방식과 무관하게 항상 수행)**: 채팅으로 컨펌하든 웹 UI로 하든, 질문을 시작하기 **전에** 추출 결과를 `.cache/review/<문서명>.json`에 반드시 저장한다. 웹 검토 목록(:57900)은 이 파일만 읽으므로 저장을 건너뛰면 사용자가 웹에서 검토할 수 없다 (2026-07-30 실제 누락 사례: 아카이브·위키 환류만 하고 검토 JSON을 저장하지 않아 목록에 미노출). 추출 결과를 `.cache/review/<문서명>.json`에 저장한다. 형식은 `90-Meta/review-ui/server.py` 상단 docstring의 검토 JSON 스펙을 정확히 따른다 (`status: "pending"`, 노드는 `{label, key, props}`, 관계마다 `evidence` 근거와 `confidence`(`direct`|`implied`) 필수). `implied` 관계에는 사용자에게 물을 자연어 확인 질문을 `question` 필드로 함께 생성한다 — 스키마 용어(ATTENDED 등)를 쓰지 않고 비서가 옆에서 묻듯 쓴다 (예: "김용이 부회장에게 보고하는 사이로 보이는데, 기록해둘까요?"). 웹 UI 카드 모드가 이 질문을 그대로 표시한다
   - **할 일 컨펌 (생략 금지)**: 회의록 `## 할 일` 표에서 뽑은 ActionItem은 관계 컨펌과 별개로 **목록 전체를 사람에게 보여 확정받는다** — 할 일은 홈 화면 '오늘 할 일'로 바로 노출되는 항목이라 한 건이라도 잘못 들어가면 매일 눈에 띈다. 채팅 경로에서는 `| # | 할 일 | 담당 | 기한 | 프로젝트 |` 표 하나로 묶어 보이고 "이대로 기록할까요? 고칠 항목은 번호로 말씀해 주세요"로 묻는다. 웹 UI(:57900) 카드 모드에는 **'할 일 확인' 카드**가 인물 확정 다음에 나와 내용·담당·기한·프로젝트를 줄 단위로 바로 고치고 확정할 수 있으며, 카드 아래 **채팅창**으로 "2번 담당은 김영희로"처럼 말로 고칠 수도 있다(`POST /api/chat` — 검토 JSON을 직접 수정). 두 경로 모두 검토 JSON의 PRODUCED/ASSIGNED_TO 관계를 고치는 것이므로 결과는 같다. 프로젝트 에이전트 드로어에는 할 일 목록을 두지 않는다(2026-08-28 제거) — 할 일의 진입점은 홈 화면과 이 컨펌 단계다
   - **채팅 컨펌은 선별 질문(triage) 방식**: 추출 결과를 번호표로 쏟아내지 않는다. ① 확실한 것(direct 근거 + 그래프에 이미 있는 인물)은 한 문장으로 묶어 일괄 확인한다 — "이번 회의 참석자를 경태, 호정, 은솔로 정리했어요. 맞나요?" ② 불확실한 것만 하나씩 개별 질문한다 — STT 추정 인명, 기존 인물과 유사한 이름("'우진연'은 기존의 '이철수'과 같은 사람인가요?"), implied 관계, 처음 보는 인물. 질문은 3~5개 이내로 묶고 일상어를 쓴다. 이미 노드 `aliases`로 확정된 표기는 다시 묻지 않는다. 웹 UI 경로(`bash 90-Meta/scripts/review_ui.sh` 기동 또는 `90-Meta/review-ui`의 docker compose, http://localhost:57900 — 카드 모드가 같은 질문 흐름 제공)도 함께 안내한다
   - **승인 대기 (채팅 경로)**: 사용자 지시를 받으면 확정분으로 Cypher 파일(`.cache/cypher/<문서명>.cypher`)을 생성하고 `bash 90-Meta/scripts/graph.sh file <경로>`로 적재한 뒤, 검토 JSON의 `status`를 `applied`로 갱신한다. 스키마와 Cypher 작성 규칙은 `90-Meta/neo4j/SCHEMA.md`를 따른다
   - **중복 적재 방지**: 작업 전 검토 JSON의 `status`를 확인한다 — 이미 `applied`(웹 UI에서 처리됨)면 재적재하지 않는다
   - **적재 후 검증**: 익명 노드 0건, `source` 누락 0건을 쿼리로 확인해 보고한다
   - 예외: 사용자가 `/ingest --auto`로 명시 호출한 경우에만 컨펌을 생략한다. 컨테이너가 내려가 있으면 검토표까지만 만들고 보고에 명시한다 (문서 처리 자체는 진행)
5. **원본 아카이브**: 처리 완료된 원본을 이동한다
   - 회의록 → `60-Sources/meetings/사용자_IN_<사업명>_<어떤업무>_V1.0_<YYYYMMDD>.md` (CLAUDE.md "문서 파일명 규칙") (비-md 원본은 변환본과 원본을 함께 보관)
   - 그 외 → `60-Sources/docs/<주제>.<확장자>`
   - 이동한 파일 상단(md인 경우 frontmatter)에 추출된 위키 노트 링크 목록을 추가해 양방향 추적을 만든다
6. **보고**: 처리한 문서 수, 생성/보강된 위키 노트, 그래프 적재 결과(노드/엣지 수), 회의록에서 나온 액션 아이템을 요약 보고한다

## 규칙

- 원본은 절대 삭제하지 않는다 (이동만)
